## Concrete defects (file:line, problem, fix)

Paths are relative to `phases/`. Severity: H = wrong or misleading statement or code, M = gap that will confuse a beginner or an interviewer, L = polish.

### Phase 01 SQL

- **D1 (M)** `01-sql/01-group-by-from-raw-rows/README.md:20`: "The database does four steps in this order:", but five steps follow. The list also leaves out SELECT and ORDER BY, so a beginner never sees the full logical order. **Fix:** "five steps", and add the whole order: FROM, WHERE, GROUP BY, aggregates, HAVING, SELECT (aliases are created here), ORDER BY, LIMIT. Explain that this is why a SELECT alias works in ORDER BY but not in WHERE in most databases.
- **D2 (M)** All SQL READMEs (for example `01-sql/01-group-by-from-raw-rows/README.md:35-42`): the walk-through says "Look at the statuses first" and shows SQL, but nowhere in the course says how to run an ad hoc query against the CSVs. The only runner is the test file. Python 3.9 has no `python -m sqlite3` CLI. **Fix:** ship `tools/sql.py <lesson-folder> "<query>"`, which reuses the tests' `load_db()` and prints a table. Add one "How to run these queries" box to the phase README and to SQL 01.
- **D3 (L)** `01-sql/01-group-by-from-raw-rows/test_lesson.py:122`: the test is named `test_busy_cities_uses_having` but does not check for HAVING. A WHERE on a subquery passes. That is acceptable SQL, so either rename the test or say in the README that any correct form passes.
- **D4 (M)** `01-sql/02-joins-without-losing-rows/README.md:68`: `COALESCE(SUM(o.amount), 0)` is the first use of COALESCE and is never explained. **Fix:** one line: "COALESCE returns the first non-NULL argument, so a customer with no orders shows 0, not NULL."
- **D5 (M)** `01-sql/02-joins-without-losing-rows/README.md:20-36`: no picture of row matching. This is the concept beginners most need to see. **Fix:** a small ASCII diagram, for example customers C1, C2, C3 against orders O1(C1), O2(C1), O3(C2), with the INNER and LEFT result rows and the NULL row for C3, plus a fan-out picture with two address rows.
- **D6 (L)** `01-sql/02-joins-without-losing-rows/README.md:119`: answer 1 says 1,000 x 1,000 giving 1,400 rows means a key "is not unique on one side". That is true, but a beginner may conclude every growth is a bug. **Fix:** "If you expected one to one, a key is duplicated. If the relationship is one to many, growth is expected; check it matches the many side's count."
- **D7 (M)** `01-sql/02-joins-without-losing-rows`: no anti-join alternatives. `NOT EXISTS`, and the `NOT IN` with a NULL trap (it returns nothing if the subquery holds a NULL), are interview staples. RIGHT/FULL OUTER JOIN and self-join are not mentioned at all. **Fix:** add NOT EXISTS as a second way in step 2, plus a Check yourself question on NOT IN with NULL.
- **D8 (H)** `01-sql/03-window-functions/README.md:3` and `:7` ("tracking against its year to date"): the data runs from 2025-10 to 2026-09 (verified) and the running total never resets at 1 January. So it is a 12-month cumulative total, not year to date. **Fix:** either say "fiscal year to date (Fernhill's year starts in October)", or partition by year so it resets. A learner who copies this pattern for calendar YTD will be wrong.
- **D9 (M)** `01-sql/03-window-functions/README.md:22-30`: the lesson spells out `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` but never says that the default frame with ORDER BY is `RANGE ... CURRENT ROW`. Under RANGE, tied ORDER BY values are summed together, a classic silent wrong answer. Months are unique here, so the test cannot catch a learner who drops the frame. **Fix:** a two-row demo with a tied date showing ROWS vs RANGE, and a test row with a tie.
- **D10 (L)** `01-sql/03-window-functions/README.md:35`: "Window functions are computed after WHERE and GROUP BY". Add "and HAVING". Also mention QUALIFY (Snowflake, BigQuery, Databricks), which interviewers on those stacks expect.
- **D11 (H)** `01-sql/04-cohort-retention/README.md:75-111`: when run, the pivot query returns **0.0** for months that have not happened yet: 2026-04 m3, 2026-05 m2 and m3, and 2026-06 m1 to m3 (verified). The table at :102-109 shows blanks, and :111 says "The blank cells are months that have not happened yet. They are not zero retention." So the code produces the exact mistake the text warns about. **Fix:** in each m_k column, wrap the expression in `CASE WHEN <months since cohort start to data end> >= k THEN ... END` (for example compare against `MAX(event_date)`), so unobserved cells are NULL. Or say plainly that the query shows 0.0 and those zeros must be blanked.
- **D12 (M)** `01-sql/04-cohort-retention/README.md:62,71,73`: CAST, "three CTEs" and "conditional aggregation" are used without definition. This is the first CTE in the course. **Fix:** a short "A CTE is a named subquery: `WITH name AS (...) SELECT ... FROM name`" before step 3, and one sentence on CASE inside an aggregate.
- **D13 (M)** `01-sql/04-cohort-retention/exercise.sql:15-16` and `solution/solution.sql`: the long form only has rows for cohort and month pairs with at least one active user. A real zero-retention month becomes a missing row, which cannot be told apart from "not observed yet". **Fix:** mention it, and optionally build the full grid with a cohorts x month_numbers cross join and a LEFT JOIN, so that zeros are real zeros.
- **D14 (M)** `01-sql/04-cohort-retention/README.md:135`: answer 3 gives the reason as "not comparable across cohorts of different sizes". That is not the problem: conditional rates are proportions and compare fine. **Fix:** "You get month to month survival, a conditional rate. It does not tell you what share of the original cohort is left. It also misbehaves when users skip a month and come back, because the month 2 actives are not a subset of the month 1 actives."
- **D15 (M)** `01-sql/04-cohort-retention/test_lesson.py`: a learner who divides by month 0 actives instead of cohort size passes. Every user has a signup-day event (verified: 0 users without one), and the README admits this at :100. **Fix:** see D50 (variant dataset). Remove one user's signup-day event in the variant.
- **D16 (M)** SQL dialect: `strftime` (SQL 04) and `SUM(t1 IS NOT NULL AND ...)` (Metrics 02) are SQLite-only. BigQuery rejects SUM(bool), and SQL Server has no boolean expressions in SELECT. **Fix:** one "In Postgres / BigQuery / Snowflake" line per lesson: `DATE_TRUNC('month', d)`, `DATE_DIFF`/`AGE`/`DATEDIFF`, `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` or `COUNTIF`.

### Phase 03 Metrics and product analytics

- **D34 (H)** `03-metrics-and-product-analytics/01-metric-trees/README.md:36`: "If revenue did not change at all, the formula divides by zero, so every effect is 0." This is wrong. If revenue is flat but the factors moved (visitors +10%, conversion -9.1%), the correct split is +228.7 / -228.7. The solution returns 0 / 0 / 0 (verified with build_tree(1000,40,2400) to build_tree(1100,40,2400)). The same rule is in `exercise.py:34` and `solution/solution.py:47-48`, and `test_lesson.py:63-66` (`test_decompose_no_change`) only tests identical trees, so the bug is locked in. **Fix:** use the logarithmic mean, `L(a,b) = (a-b)/(ln a - ln b)` with `L(a,a) = a`, and `effect_f = L(R1,R0) * ln(f1/f0)`. Add a test where revenue is flat and the factors offset. Name the method (LMDI) so learners can look it up.
- **D35 (M)** `03-metrics-and-product-analytics/01-metric-trees/solution/solution.py:45,50`: `math.log` raises "math domain error" when any factor or revenue is 0. For example, a channel slice with zero orders, which `build_tree` explicitly returns as 0.0 conversion. Drill-downs hit this case in real data. **Fix:** document it, and return None or "n/a" for the slice, with a sentence on why log methods cannot handle zeros.
- **D36 (M)** `03-metrics-and-product-analytics/01-metric-trees/README.md:20-26`: a lesson called "Metric trees" has no tree drawing. **Fix:** an ASCII tree with the lesson's numbers, for example `revenue $30,971 (-3,825)` branching to `visitors 18,261 (+380)`, `conversion 2.90% (-5,051)`, `aov $58.44 (+846)`, with the channel split under conversion.
- **D37 (M)** `03-metrics-and-product-analytics/01-metric-trees/README.md:28-34`: natural logs arrive with no intuition for a zero-background reader. **Fix:** one worked line showing that logs turn multiplication into addition (ln(2 x 3) = ln 2 + ln 3), then the formula.
- **D38 (L)** `03-metrics-and-product-analytics/01-metric-trees/README.md:82`: "even though no single channel changed its prices". Per-channel AOV did move a little (email 62.25 to 63.97). **Fix:** "no channel's AOV moved by more than about 3%."
- **D39 (M)** `03-metrics-and-product-analytics/02-funnel-conversion/README.md:37` and `solution/solution.sql:27-30,61-64`: `SUM(t1 IS NOT NULL AND t2 >= t1)` relies on SQLite turning comparisons into 0/1 (see D16). The README also never notes that comparing text timestamps only works because of the ISO format. **Fix:** a dialect note, and the portable `SUM(CASE WHEN ... THEN 1 ELSE 0 END)`.
- **D40 (M)** `03-metrics-and-product-analytics/02-funnel-conversion/README.md:130`: answer 4 says a 24-hour window means "users who have not had time to finish are not counted as lost". A window alone does not do that. You also have to exclude users whose first view is less than 24 hours before the end of the data (right censoring). **Fix:** add that clause.
- **D41 (M)** `03-metrics-and-product-analytics/02-funnel-conversion/README.md:105,128`: "pick the step with the lowest step conversion" and "Spend the sprint on the course page". The same relative improvement at any step moves purchases by the same percentage, and top-of-funnel steps naturally convert lower because of browsing intent. **Fix:** frame the choice as achievable lift x cost per step. Keep the course page as a hypothesis, not a verdict.
- **D42 (L)** `03-metrics-and-product-analytics/02-funnel-conversion/README.md:94`: UNION ALL is used without explanation. Add one line.
- **D43 (H)** `03-metrics-and-product-analytics/03-active-users-and-stickiness/README.md:79`: "Average DAU drops by almost two thirds, because most daily opens are notification taps from people who do not work out." The lesson's own data contradicts this. Of 1,453 app_open rows, only 266 (18%) come from users who never log a workout. 916 (63%) are opens on a day the user did not log a workout, mostly by people who work out on other days. The data also has no notification flag. **Fix:** "because most opens happen on days with no workout logged."
- **D44 (M)** `03-metrics-and-product-analytics/03-active-users-and-stickiness/README.md`: no visual. **Fix:** an ASCII user x day grid (5 users x 7 days, with marks) showing DAU per column, WAU as the union, and why the sum of DAU is not WAU.

With about 658 control applications, the SE of the reply-rate difference is about 1.8 points, so the 2-point tolerance is roughly one SE and could trip by chance. **Fix:** make the rule "north star lift significant and at least +2 points; guardrail CI lower bound not worse than -2 points" (a non-inferiority framing). Step 3's z-test then becomes part of the rule rather than an aside.
- **D46 (M)** `03-metrics-and-product-analytics/04-north-star-and-guardrails/README.md:88`: "unsubscribes went down". That is 21 vs 16 events, which is noise. ## What is excellent and must be preserved

- **The contract works and is reproducible.** All 12 solutions pass and all exercises fail. Every CSV regenerates byte-identically on Python 3.9.6. Every README code block runs, and its printed numbers match the prose (11 of 12 lessons perfectly; see D11).
- **Independent verification inside the tests.** Expected answers come from a plain Python loop, never from the solution file. The SQL 01 test docstring makes the point: the test is a second way of doing GROUP BY. Keep this pattern.
- **Every lesson has a trap with a real wrong number.** Fan-out 465 rows vs 360. Dashboard checkout 14.7% vs 40.3% by users. MAU 170 vs 85. ROW_NUMBER dropping a tied rep from the bonus list. z instead of t margin 7.18 vs 7.73. AOV rising as a mix artifact. This is the course's signature, and it is what interviews test.
- **"What to tell <stakeholder>" sentences.** These turn a calculation into a decision, which is the job-ready skill most courses skip. (Fix D23 and D43 so the copied sentences are right.)
- **Check yourself answers with nuance.** The CI definition (Stats 02), the p-value as P(data | null) (Stats 03 answer 2), peeking, WHERE after a LEFT JOIN, LAG over a calendar gap, blank vs zero cohort cells, the CEO "ship anyway" answer as an explicit trade.
- **Analogies that land.** "GROUP BY is a loop with a dictionary", the window as "like GROUP BY, but no collapse", "a trailing window is a union of daily sets, not a sum of daily counts".
- **Honest statistical caveats already present.** Cohort April lift "a lead, not a result". The reply rate is per application, so a plain z-test overstates precision. The Wald condition is checked against the actual counts (129 / 271).
- **Clean style.** No em or en dashes, no curly quotes, synthetic data labelled in every lesson, and job-feed numbers dated and linked.
